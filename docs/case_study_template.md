# Real use case record

Use this for an actual user task. Synthetic demonstrations and maintainer
regression runs should be labeled separately. Reporting a stable outcome or no
decision change is useful evidence too.

## Before the audit

- Task, actual user role, date and software version/commit:
- Decision to make (model selection, scoring specification or another choice):
- Original plan and the evidence supporting it:
- Data source, sampling, sample size, pairing and reference-label review:
- Rules included and the task-specific reason for each:
- Rules excluded, why, and when these choices were fixed:
- Consent and redistribution permission; share only approved data:

## Run and inspect

- Installation route, prior familiarity and help received:
- Time to first usable result; errors, confusion and failed attempts:
- Commands/UI steps and a replayable JSON report or approved redacted substitute:
- Main justified-family result and endpoint rules:
- Tie counts and strict reversal counts, separately:
- Optional stress-family results, clearly separated:
- What was checked manually on reference labels and extraction examples:

## After the audit

- Actual decision: unchanged, more data requested, scoring revised, model changed,
  or another documented action:
- Which finding influenced that action, and supporting user statement/artifact:
- Follow-up outcome and cost/time, if observed:
- Remaining uncertainty or alternative explanation:
- Who performed the run and who assessed the outcome:

Avoid calling an automated replay an independent human usability trial. A
friend's source review is technical feedback; it becomes first-use evidence only
when the actual task, steps, assistance and observed outcome are recorded.
